# Native acceptance and real delivery loop

User intent: complete ordinary-chat task delivery with native acceptance binding, demonstrate stability with fixed-condition repeated real tasks, and publish a verified macOS installation release on GitHub. Continue autonomously within the existing $10 real-model budget. A green local suite or one external benchmark is not the full completion criterion.

Evidence at baseline 4a63aaf: INCACHE six rounds complete and independent functional C=70/70 under $1/1200s; native acceptance=[] and delivery=unverified. Sustained goals already support structured acceptance plus VerificationService. Ordinary direct work has no model-facing way to bind checks without switching to a sustained goal.

Approaches considered: require every command/edit to start a goal (breaks ordinary bounded work); infer acceptance from successful commands (cannot prove semantics); expose an explicit ordinary-task binding and core-owned validation (selected). Preserve the existing sustained goal path.

The ordinary tool `bind_task_acceptance` takes the current expected_revision, structured criteria and named verification commands. It is available only in native chat work. It persists a bounded plan atomically, adds required criteria without removing existing criteria, records the model's authorship and the real user requirement IDs, and never records a pass or executes commands itself. Rebinding an identical plan is idempotent. Unknown steps, unsafe paths, stale revisions, missing live authorization and active sustained-goal intake fail without partial state. A same-name command cannot silently replace an earlier command; add a new name instead.

At normal ordinary-chat delivery, the core runs the current bound plan through VerificationService with existing permissions, stage restrictions, cancellation, fingerprints and durable evidence. Reuse successful evidence only when task identity, revision, complete configuration and current file fingerprint match. Never treat assistant prose or plain run_command success as acceptance. New requirements require a renewed plan; file changes require fresh execution. Preserve failed/denied/unknown/cancelled outcomes. Native reports identify agent-declared coverage separately from explicit user declarations; they do not assert semantic completeness beyond the declared coverage. Independent test oracles remain necessary.

Acceptance: normal model/tool/permission execution can bind, implement and produce verified current evidence; deliberate check failure cannot verify; denial starts no process; new user requirements and out-of-band edits invalidate old proof; revision/identity changes during approval fail closed; existing goal/manual/read-only/explicit-tool-list behavior remains intact. No requirement, original test or data deletion to pass.
