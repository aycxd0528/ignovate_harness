项目：奶龙 Agent / LLM_project

**核心判断**

当前项目已经具有实质性的 Agent 工程实现，适合作为学习、作品展示和持续实验的平台。权限审批、会话恢复、上下文管理、任务状态、证据验收、用量控制和 MCP 接入均有代码支撑。主要短板是功能增长快于稳定性、可维护性和真实任务效果验证。

后续应围绕用户明确提出的三个目标发展：**保持任务连续性、用真实证据交付、及时停止无效工作**。建议用同模型跨 Agent 实验发现问题，在自己的项目中验证改进效果；GUI 则逐步成为共享内核的任务与证据展示、控制入口。

本次全量测试的三项异常分别涉及审批恢复预算测试中假运行时输出耗尽、headless 测试预期的旧参数缺失，以及 CLI 预算错误文案与断言不一致。它们表现出接口和测试同步问题，不能直接当作三个已确认的实际使用故障，但当前版本确实尚无全绿基线。

主要优点：

- **执行层有约束。** 权限、模式和文件版本在执行入口检查，审批等待期间的文件变化也会影响后续执行。
- **验收有证据意识。** 交付判定考虑证据来源、任务版本、输入指纹和覆盖范围，能够识别过期证据。
- **可靠性投入较多。** 测试包含取消、越权、恢复和证据失效等异常路径，文档记录了部分真实 API 验收。
- **具备界面复用基础。** AgentService、TurnEvent、TaskStore 等已经承载了共享逻辑。

主要不足：

- **复杂度集中。** 核心回合同时处理流式输出、审批、预算、任务状态和收尾，修改容易相互影响。
- **版本与交付基础不足。** 已提交仓库不能完整复现当前工作区，自动化回归与依赖复现仍需补齐。
- **真实效果尚缺系统评测。** 离线测试和冒烟通过不足以证明复杂任务成功率、长期约束保持和停止策略有效。
- **上下文恢复仍依赖模型行为。** 压缩使用关键词和节选，原文可归档恢复，但模型是否及时回读需要验证。
- **规模边界明确。** 完整输入指纹设有 5,000 文件／50 MiB 上限；大仓库性能和验证体验仍需专门评估。

已有冒烟记录中的一次极短回答使用了 9,811 个输入 token。这是检查固定提示与工具定义开销的线索，单个样本不足以代表整体效率。

**三、围绕三个目标的内核发展方向**

| 目标 | 建议补强的能力 | 关键验收场景 |
|---|---|---|
| 任务连续性 | 区分查询、补充、修改、恢复、取消和新任务；记录约束来源与替代关系 | 问进度不改变执行状态；后续纠正准确替代旧要求 |
| 中断后继续 | 有副作用操作保存稳定 ID、执行前条件和执行状态；结果未知时先核对实际状态 | 文件已修改但结果尚未保存时退出，恢复后不盲目重做 |
| 真实证据交付 | 将用户要求、验收项、执行证据和版本关联 | 测试通过后相关文件变化，旧结果不能支持新交付 |
| 停止无效工作 | 记录尝试目的、动作、观察和新增证据，识别重复失败与循环 | 明显无效循环及时停止；正常探索和可修复问题不过早停止 |

当前任务更新逻辑通常会因新的用户文本递增版本、使证据失效；普通用户回合还可能重置停滞记录并激活暂停任务。因此，“现在进展如何？”这类状态询问应成为优先验证的边界场景。见 [任务状态实现](/Users/aycxd/Desktop/LLM_project/nailong/core/task_state.py:194)。

操作恢复建议区分“准备执行、执行中、成功、失败、结果未知”。图检查点能够保存运行状态，但外部副作用仍需要业务层核对；结果未知不应直接等同于失败。LangGraph 官方文档说明了检查点、线程及恢复边界，可作为实现参考。[检查点文档](https://docs.langchain.com/oss/python/langgraph/checkpointers)

证据应限制结论的范围：某个复现测试通过可以支撑该场景已验证，不能自动推导所有行为正确。保留原有回归测试，记录测试自身的修改。相关验收已通过且输入没有变化时，应完成交付，避免重复验证。

目前重复检测主要识别连续相同的成功读取。后续应覆盖交替读取、重复失败命令和修改反复回退等尝试序列，同时保留正常分页、等待和排除假设的空间。见 [进展检测](/Users/aycxd/Desktop/LLM_project/nailong/core/progress.py)。

建议停止时稳定输出四项：**已完成内容、已尝试方法、停止原因、恢复条件**。停止次数需要与成功率和误停次数一起观察。

**四、同模型跨 Agent 实验设计**

实验目标是找出不同 Agent 配置如何影响任务连续性、证据交付和失败处理，并形成奶龙 Agent 的可验证改进。结论应限定在所选任务、版本和配置范围内。

| 实验分组 | 配置 | 可以解释的差异 |
|---|---|---|
| 主实验 | Kimi Code、TRAE、Claude Code、DeepSeek Harness、奶龙 Agent，统一 DeepSeek V4.1 Flash | 同模型下不同 Agent 整体配置的表现 |
| 产品参考组 | Codex＋GPT-6.1 Sol | 该完整系统在同一任务上的表现 |
| 可选模型对照 | 同一 Agent 分别使用 DeepSeek 与 GPT-6.1 Sol | 在该 Agent 中更换模型的影响 |

Codex＋GPT-6.1 Sol 同时改变模型和 Agent，不能独立用于归因模型差距，也不能作为无需验收的标准答案。

本次讨论查阅的官方资料表明，Kimi Code CLI 支持 DeepSeek 所用的 OpenAI 兼容协议，TRAE 支持自定义模型，DeepSeek 提供 Claude Code 接入教程。接入路径可行不等于所有具体版本和模式已验收；正式运行前需要预检工具调用、文件修改、测试和会话恢复。

需要记录实际模型来源，包括子代理、摘要调用和自动回退。按本次查阅的 DeepSeek 更新文档，V4.1 Flash 使用 `deepseek-flash` 调用；别名可能随时间更新，应记录日期及可获得的响应元数据。Claude Code 接 DeepSeek 的结果属于该兼容组合，Anthropic 不为通过网关接入非 Claude 模型提供支持。

实验条件建议固定：

- 起始 Git 提交、依赖、输入数据、任务文本和验收规则。
- 模型服务来源、可配置推理和输出参数、时间与费用上限。
- 外部工具与网络权限，以及预先约定的审批、人工提示规则。
- Agent 版本、工作模式、插件和配置；每次使用隔离目录及全新会话、记忆。

保留并记录 Agent 自身的系统提示、工具定义和上下文策略，因为它们也是比较对象。顺序交错运行，保留失败运行和临场干预记录。无法统一或观察的变量需在结论中说明。

任务可以沿用“日志扫描 CLI 增加持久增量缓存”，增加固定的需求纠正、进度询问、中断恢复、证据失效及外部阻塞场景。阻塞探针还应配可修复场景，以识别误停；未实际发生压缩的运行不能记作已测试压缩后的连续性。

建议起步规模为 **5 个同模型主实验组（含奶龙 Agent）＋1 个 Codex 产品参考组，每组 3 次，共 18 次运行**；可选模型对照不计入这 18 次。这个规模用于探索失败模式，不足以支持普遍领先的结论。后续扩展任务种类并保留不参与调参的任务。每个阶段的规则要一致：新增 `--force` 后，“CLI 不变”应解释为原有接口兼容，不能继续机械要求全部 `--help` 文本无变化。

**五、数据处理与结果归因**

建议使用 Codex 编写和运行数据处理脚本、整理记录及分析失败模式。评分尽量依赖可复现产物：

原始日志与最终文件 → 脚本提取指标 → 独立测试验收 → Codex 分析 → 人工抽查。

| 维度 | 建议保留的指标 |
|---|---|
| 任务结果 | 功能测试、回归测试、约束遵守情况 |
| 连续性 | 需求纠正是否生效、中断恢复结果、重复副作用 |
| 交付可信度 | 缺乏证据或使用过期证据的完成声明 |
| 停止质量 | 无效重试、停止时点、误停、恢复条件是否明确 |
| 使用成本 | 人工干预、耗时、实际 token 和费用 |

缺失数据标为未知。主观判断尽量匿名化 Agent 名称，并附日志位置；分析使用独立上下文。先展示分项，再决定是否合成总分。Agent 评测应检查最终环境状态、重复运行，并同时覆盖应触发和不应触发的情形。[评测参考](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

现有 [对比报告模板](/Users/aycxd/Desktop/LLM_project/docs/agent-comparison/2026-10-05-跨架构对比测试报告-模板.md:7) 中“全部失败归因模型、部分失败归因脚手架”的规则需要修改。共同失败可能来自任务或环境，部分失败也可能来自随机性、配置和协议适配。

建议采用：**观察失败 → 定位调用与上下文 → 提出原因假设 → 在奶龙中只修改相关机制 → 重跑原任务与保留任务**。实验产出应包括失败案例、证据、改进假设和复测结果。

**六、共享内核的 GUI 路线**

讨论建议保留 CLI、Textual 和 headless，让 GUI 通过共享应用服务使用同一内核。推荐的逻辑关系为：

| 层次 | 责任 |
|---|---|
| CLI／Textual／GUI／评测程序 | 收集输入、展示事件和结果 |
| 共享应用服务 | 提交请求、队列、审批、暂停、恢复和会话协调 |
| Agent 内核 | 任务状态、模型、工具、权限、验证与停止判定 |
| 持久存储 | 状态快照、执行事件、证据与产物 |

现有 AgentService、TurnEvent、TaskStore 可以复用，但计划与目标循环仍位于 [ui/flows.py](/Users/aycxd/Desktop/LLM_project/ui/flows.py)，headless 也调用 ui 下的命令逻辑。后续可按实际接口需求逐项整理边界。

共享内核还应保证同一任务由一个运行实例负责执行、多个界面可以观察；审批绑定操作与版本，重复提交不重复执行；刷新后能通过快照与事件序号恢复；窗口关闭、暂停、取消有明确区别；完成与验证状态由内核产生。

第一版 GUI 建议包含项目与任务列表、执行时间线、目标与约束详情、diff 与证据查看，以及逐步加入的输入和审批控制。重点交互是从“需求已验证”直接查看对应测试、版本和日志。完整代码编辑器、终端模拟器、插件市场和复杂多代理视图暂列后续候选。

技术路线建议优先考虑 **Python 内核＋本地服务＋Web GUI**。待交互和服务边界稳定，并有安装、通知、文件关联等实际需求后，再选择桌面壳与打包方案。密钥、文件访问、命令和权限管理继续由后端负责。

GUI 的关键验收条件：从 CLI 或 GUI 发起同一测试任务时，权限决定、任务状态、证据判定和停止行为一致；刷新界面不会丢失或重复操作。

**七、建议推进顺序与待明确事项**

| 阶段 | 主要工作 | 验收依据 |
|---|---|---|
| 1. 建立稳定基线 | 处理现有测试异常，补齐版本跟踪、依赖复现和自动检查，冻结参测版本 | 可复现的基线及配置记录 |
| 2. 实验预检 | 固定任务、分组、扰动时点、预算、人工干预及日志格式 | 各工具接入与基本操作通过预检 |
| 3. 首轮对比 | 五个同模型组与一个 Codex 参考组各运行三次，采集产物和失败记录 | 独立验收结果及带证据的分析 |
| 4. 内核改进 | 优先验证消息分类、恢复、证据关联和停止机制 | 原场景改善，保留任务无明显回归 |
| 5. 只读 GUI | 展示本地任务、时间线、diff、证据和停止原因 | 能支持实验分析与日常排查 |
| 6. 交互 GUI | 接入共享应用服务，支持审批、暂停和恢复 | 跨界面语义一致，重连不重复执行 |
| 7. 桌面分发 | 根据使用需求确定打包和系统集成 | 安装、升级和使用体验验收 |

任务规模、TRAE 版本与模式、各组预算、推理设置、人工介入规则和是否增加同 Agent 的模型对照，仍需在实验协议中确定。GUI 的具体前端和桌面壳尚未选型。现有实现、实验设想与架构建议应分别保留状态，避免将讨论意见记录为已完成能力。
